ชีทอ่านโค้ดระบบ Rider และตอบคำถามโปรเจกต์

สรุปจากโค้ดปัจจุบัน แบ่งตามหน้า ระบบ และวิธีคำนวณ เพื่อใช้เรียน อธิบายงาน และตอบคำถามอาจารย์

เป้าหมาย รับออเดอร์ช่วงเช้า จัดกลุ่ม Rider ไม่เกิน 3 ออเดอร์ต่อรอบ ออกส่งประมาณ 11:30 น. และพยายามส่งให้ทัน 12:30 น. โดยลดระยะทางและต้นทุน

1. ภาพรวมระบบ

Angular Frontend → HTTP API → Express Backend → SQL → Neon PostgreSQL

Frontend แสดงหน้าจอและรับการกดปุ่ม, Backend ตรวจข้อมูลและทำงานกับฐานข้อมูล, Database เก็บข้อมูลถาวร

จุดเริ่ม Backend คือ backend/server.ts; การตั้ง CORS และ Mount API อยู่ใน backend/app.ts

ส่วนหน้าที่หลักฐาน
Frontendหน้าเว็บ แผนที่ ฟอร์ม และเรียก APIfrontend/src/app/pages/
Backendตรวจข้อมูล SQL คำนวณ และคืน JSONbackend/controller/, backend/services/
Databaseร้าน ลูกค้า Rider ออเดอร์ แผน และจุดส่งbackend/database/rider_project_seed_v2.sql

5. วงจรสถานะ

PENDING → ASSIGNED → DELIVERED

  • PENDING รอดำเนินการ แก้/ลบ/จัดเส้นทางได้
  • ASSIGNED ถูกผูกกับใบงานแล้ว ไม่ควรแก้/ลบโดยตรง
  • DELIVERED ส่งสำเร็จและย้อนกลับไม่ได้จากหน้า Rider
  • ยกเลิกใบงานได้เมื่อทุกจุดยัง PENDING; ระบบคืนออเดอร์เป็น PENDING, ลบ route_stops และเปลี่ยน route_plan เป็น REJECTED

6. ลำดับการจัดเส้นทาง

  1. โหลดร้านและวันธุรกิจจาก GET /route-plans/planning-store
  2. โหลดออเดอร์ Rider และแผนเดิมพร้อมกันด้วย Promise.all
  3. ส่งพิกัดร้านและลูกค้าไป POST /route-plans/road-matrix
  4. สร้างทางเลือกจาก nearest, sweep และ farthest-seed
  5. เลือก Rider ที่ AVAILABLE และไม่เกิน 3 ออเดอร์ต่อรอบ
  6. เริ่มจากร้าน แล้วเลือกจุดใกล้ตำแหน่งล่าสุด
  7. ลองลำดับจุดและปรับกลุ่มตามตัวชี้วัดจำนวนงาน ความสาย ต้นทุน และระยะทาง
  8. คำนวณเวลา ต้นทุน รายรับ กำไร และคำเตือน
  9. ร้านเลือกแล้วส่ง POST /route-plans/confirm เพื่อบันทึกจริง

จำให้ชัด: OSRM ให้ระยะทาง/เส้นถนน ส่วน Algorithm ของโปรเจกต์เป็นคนแบ่งกลุ่มและเลือกแผน

สูตรระยะทาง

Haversine: a = sin²(Δlat/2) + cos(lat1) × cos(lat2) × sin²(Δlon/2)
distance = 6371 × 2 × atan2(√a, √(1-a))

โค้ดอยู่ที่ planning/route-distance.ts; การวางแผนจริงใช้ Matrix ถนนจาก OSRM ใน backend/services/road-matrix.ts

สูตรเวลา

นาทีเดินทาง = ระยะทางกม. ÷ ความเร็ว กม./ชม. × 60
ออก 11:30, เส้นตาย 12:30, ถึงตรงเวลาเมื่อเวลาถึง <= 12:30

ความเร็วเริ่มต้นคือ 30 กม./ชม. ใน planning/route-timing.ts เป็นค่าประมาณ ไม่ใช่ GPS แบบ Real-time

สูตรต้นทุน

รายรับ = กล่อง × 65
ต้นทุนอาหาร = กล่อง × 40
ค่ารอบ = 15 ต่อเที่ยว
ค่าระยะทาง = ระยะทาง × กล่อง × 2
ค่าปรับประมาณ = ออเดอร์ที่ช้า × 20
กำไร = รายรับ - ต้นทุนทั้งหมด

สูตรจริงอยู่ที่ planning/route-cost.ts

8. Login ของ Rider

QR/กรอก code → POST worksheet → เก็บ code → ส่ง x-worksheet-code → Backend หา rider_id/route_plan_id

  • Backend ตรวจ code, วันปัจจุบัน, ใบงานสถานะ SELECTED และ Rider ไม่ INACTIVE
  • Rider ไม่ส่ง rider_id เพื่อขอดูงานเอง; Backend เป็นผู้ระบุตัวตนจากใบงาน
  • CORS/Header สำคัญอยู่ใน backend/app.ts และ middleware/rider-session.ts

9. คำถามอาจารย์และคำตอบ

ทำไมมี route_plans กับ route_stops?
แยกใบงานระดับ Rider/สรุป ออกจากรายละเอียดจุดส่งและลำดับ

ทำไมไม่แบ่งตาม order_id?
เพราะต้องใช้พิกัดและระยะทางเพื่อให้จุดใกล้กันอยู่กลุ่มเดียวกัน

OSRM ทำอะไร?
หาเส้นถนนจริงและระยะทาง ไม่ได้ตัดสินใจแบ่ง Rider

ทำไม Rider บางคนไม่มีงาน?
จำนวนออเดอร์หรือความจุไม่พอให้ทุกคนมีงาน จึงแสดงงานเป็น 0 ได้

ทำไมต้อง Snapshot ตอนยืนยัน?
ป้องกันข้อมูลที่คำนวณไว้ไม่ตรงกับฐานข้อมูลล่าสุด

ถ้ายกเลิกใบงานล่ะ?
ถ้ายังไม่มีจุดส่งสำเร็จ/ล้มเหลว ระบบคืนออเดอร์เป็น PENDING และสร้างใหม่ได้

13. อธิบายการทำงานตั้งแต่ต้นจนจบ

ภาพรวมแบบเล่าเป็นเหตุการณ์

  1. ร้านมีข้อมูลร้านอยู่ใน stores และมีลูกค้าอยู่ใน customers โดยลูกค้าแต่ละคนมีพิกัดละติจูด/ลองจิจูด
  2. ลูกค้าหนึ่งคนสั่งอาหาร ระบบบันทึกเป็นแถวใน orders พร้อมจำนวนกล่อง วันที่สั่ง และสถานะเริ่มต้น PENDING
  3. เมื่อถึงเวลาจัดส่ง หน้า delivery-routes โหลดออเดอร์วันนี้ Rider ที่พร้อมรับงาน และตำแหน่งร้าน
  4. Frontend ส่งพิกัดไปขอระยะทางตามถนนจาก Backend/OSRM แล้วนำระยะทางนั้นไปจัดกลุ่มและเรียงลำดับจุดส่ง
  5. ระบบสร้างตัวเลือกหลายแบบ เช่น เลือกจุดใกล้ร้านก่อน, กวาดตามทิศทาง และเริ่มจากจุดไกล แล้วเปรียบเทียบผล
  6. ร้านตรวจจำนวนออเดอร์ กล่อง ระยะทาง เวลา ต้นทุน และกำไรบนหน้าจอ จากนั้นกดยืนยัน
  7. Backend บันทึก route_plans เป็นใบงานระดับ Rider และบันทึก route_stops เป็นจุดส่งแต่ละจุด พร้อมเปลี่ยน Order เป็น ASSIGNED
  8. ร้านเปิดหน้า riders เพื่อดูว่า Rider คนใดมีงาน มีทั้งหมดกี่ออเดอร์ กี่กล่อง และแสดง QR/เลขใบงาน
  9. Rider กรอกเลขใบงานที่ /rider/login ระบบตรวจใบงานของวันนั้น แล้วพาไป /rider/work
  10. Rider กดดูแต่ละจุดส่ง เปิด Google Maps และเปลี่ยนผลเป็นส่งสำเร็จหรือส่งไม่สำเร็จ

14. แยกหน้าร้านกับหน้ามือถือของ Rider

กลุ่มผู้ใช้หน้าที่หลักสิ่งที่ไม่ควรทำ
ร้านค้าจัดการลูกค้า ออเดอร์ Rider คำนวณและยืนยันเส้นทางไม่ควรให้ร้านแก้ผลส่งแทน Rider โดยไม่มีเหตุผลหรือประวัติ
Riderเปิดใบงานของตนเอง ดูลำดับจุดส่ง นำทาง และรายงานผลไม่ควรเห็นใบงานของ Rider คนอื่นจากการแก้ rider_id ใน URL
Backendตรวจสิทธิ์ ตรวจสถานะ คำนวณ และควบคุมการบันทึกไม่ควรเชื่อข้อมูลสำคัญจากหน้าจอโดยไม่ตรวจซ้ำ

15. อ่านหน้า Customers แบบเข้าใจโครงสร้าง Angular

ให้เริ่มจากไฟล์ TypeScript ของหน้า เพราะเป็นตัวควบคุมข้อมูลและเหตุการณ์ แล้วค่อยอ่าน HTML ที่นำข้อมูลไปแสดง

  1. ไฟล์ customers.ts ประกาศ Component, import API service, สร้างตัวแปรข้อมูลลูกค้า, loading/error และฟังก์ชันโหลด/เพิ่ม/แก้/ลบ
  2. ไฟล์ customers.html ใช้ template syntax เช่น {{ value }}, @if และ @for เพื่อแสดงข้อมูลตามสถานะ
  3. ไฟล์ CSS ของหน้า ใช้จัดรูปแบบเฉพาะหน้า แต่โครงสร้างหลักยังอยู่ใน HTML และ class ที่ใช้ร่วมกับธีม
  4. API service ซ่อนรายละเอียด HTTP ไว้ ทำให้ Component เรียกเมธอด เช่นโหลดลูกค้า โดยไม่ต้องเขียน URL ซ้ำทุกจุด

แนวคิดสำคัญคือ Component ไม่ควรต่อฐานข้อมูลเอง แต่เรียก Service → Service เรียก Backend → Backend เรียก PostgreSQL

16. อ่านหน้า Orders แบบเข้าใจข้อมูลจริง

ข้อมูลบนหน้าจอมาจากไหนใช้ทำอะไรต่อ
ชื่อลูกค้า เบอร์ ที่อยู่customers ผ่าน JOIN กับ ordersแสดงให้ร้านตรวจออเดอร์และใช้เป็นจุดส่ง
จำนวนกล่องorders.box_quantityรวมเป็นจำนวนกล่องต่อใบงานและคำนวณรายรับ
วันที่สั่งorders.order_dateแยกออเดอร์วันนี้ออกจากวันเก่า
สถานะorders.statusกำหนดว่าจะแก้ ลบ จัดส่ง หรือจัดเส้นทางได้หรือไม่
พิกัดcustomers.latitude/longitudeคำนวณระยะทางและวาดจุดบนแผนที่

ทำไมออเดอร์เก่าถึงไม่ควรปนกับวันนี้

ระบบใช้วันที่ธุรกิจเป็นตัวกรอง หากนำออเดอร์เมื่อวานไปคำนวณวันนี้ จะทำให้จำนวนกล่อง รายรับ และใบงานผิดวัน ดังนั้นหน้า Orders และ Delivery Routes ต้องโหลดข้อมูลด้วยวันที่เดียวกันเสมอ และ Backend ต้องเป็นผู้ตรวจวันที่อีกชั้นหนึ่ง

ประโยคตอบอาจารย์: “ออเดอร์เป็นข้อมูลถาวร แต่การจัดส่งเป็นงานตามวัน จึงต้องแยกด้วย order_date และ route_date ไม่ใช่ดูจากสถานะอย่างเดียว”

17. การคำนวณระยะทาง: เส้นตรงกับถนนจริง

ระยะทางเส้นตรง ใช้สูตร Haversine เพื่อประมาณระยะห่างจากพิกัดสองจุด เหมาะสำหรับคัดกรองหรือจัดกลุ่มเบื้องต้น แต่รถวิ่งตามถนนจริงไม่ได้วิ่งเป็นเส้นตรง

distance = 2R × asin( sqrt( sin²(Δlat/2) + cos(lat1)cos(lat2)sin²(Δlon/2) ) )

ระยะทางถนนจริง ใช้ OSRM Table API เพื่อคำนวณระยะทาง/เวลาแบบหลายจุดพร้อมกัน และใช้ OSRM Route API เพื่อขอ geometry สำหรับวาดเส้นตามถนนบนแผนที่

ดังนั้น MapTiler/Leaflet มีหน้าที่แสดงแผนที่ ส่วน OSRM มีหน้าที่คำนวณเส้นทางรถ ไม่ควรใช้เส้นตรงจากการเชื่อมจุดแทนถนนจริงเมื่อแสดงผลสุดท้าย

18. วิธีคิดการแบ่งงานให้ Rider

ข้อจำกัดหลักคือ Rider หนึ่งคนรับได้ไม่เกิน 3 ออเดอร์ต่อรอบ ระบบจึงต้องทำให้ทุกออเดอร์ถูกจัดให้ Rider ที่พร้อมรับงาน และไม่เกินความจุ

  1. ตัด Rider ที่สถานะไม่พร้อมออก
  2. เลือกออเดอร์ที่ยัง PENDING และอยู่ในวันปัจจุบัน
  3. เริ่มต้นจากร้าน ไม่ใช่จาก Rider หรือจุดสุ่ม
  4. เลือกจุดถัดไปที่มีต้นทุนการเดินทางต่ำที่สุดจากตำแหน่งปัจจุบัน หรือใช้วิธี sweep ตามทิศทาง
  5. เติมจุดให้ Rider ไม่เกิน 3 ออเดอร์
  6. เมื่อเต็มหรือไม่มีจุดเหมาะสม ให้เริ่มกลุ่มของ Rider คนถัดไป
  7. เปรียบเทียบหลายทางเลือกด้วยจำนวนออเดอร์ที่จัดได้ ออเดอร์ล่าช้า กำไร เวลา และระยะทาง

การจัดกลุ่มไม่ควรใช้ order_id อย่างเดียว เพราะเลขออเดอร์ไม่ได้บอกว่าลูกค้าอยู่ใกล้กันหรือไม่

19. สูตรเวลาและเงื่อนไขหนึ่งชั่วโมง

สิ่งที่คำนวณสูตร/แนวคิดความหมาย
เวลาเดินทางระยะทาง ÷ ความเร็ว × 60แปลงชั่วโมงเป็นนาที
เวลารวมเวลาเดินทาง + เวลาจอดส่งแต่ละจุดเวลาที่ Rider ใช้จริงโดยประมาณ
เวลาถึงโดยประมาณเวลาออก 11:30 + เวลาสะสมตรวจว่าถึงก่อน 12:30 หรือไม่
สถานะล่าช้าเวลาถึงเกิน Deadlineใช้เปรียบเทียบทางเลือกและประเมินค่าปรับ

ค่าความเร็ว 30 กม./ชม. เป็นค่าประมาณเพื่อการวางแผน ไม่ใช่การรับประกันเวลาจริง เพราะรถติด ฝน และเวลาหาลูกค้าอาจทำให้ช้ากว่าโมเดล

20. สูตรต้นทุน รายรับ และกำไร

รายรับ = จำนวนกล่อง × ราคาขายต่อกล่อง
ต้นทุนอาหาร = จำนวนกล่อง × ต้นทุนอาหารต่อกล่อง
ค่ารอบ Rider = จำนวนเที่ยว × ค่ารอบ
ค่าระยะทาง = ระยะทางรวม × จำนวนกล่อง × ราคาต่อกิโลเมตรต่อกล่อง
ค่าปรับคาดการณ์ = จำนวนออเดอร์ที่เสี่ยงส่งช้า × ค่าปรับต่อออเดอร์
กำไร = รายรับ - (ต้นทุนอาหาร + ค่ารอบ + ค่าระยะทาง + ค่าปรับ)

ตัวอย่างจากค่าที่ใช้ในโค้ด: อาหาร 65 บาท/กล่อง, ต้นทุนอาหาร 40 บาท/กล่อง, ค่ารอบ 15 บาท/เที่ยว, ค่าระยะทาง 2 บาทต่อกิโลเมตรต่อกล่อง และค่าปรับคาดการณ์ 20 บาทต่อออเดอร์ที่ล่าช้า

ต้องระวังไม่สับสนระหว่าง ระยะทางของเที่ยว กับ จำนวนกล่อง เพราะค่าระยะทางคิดตามทั้งสองตัว

21. ทำไมต้องมี route_plans และ route_stops

route_plans คือหัวใบงาน เช่น Rider คนที่ 1 มีงานวันที่เท่าไร ระยะทางรวมกี่กิโล ใช้เวลากี่นาที รายรับและกำไรเท่าไร

route_stops คือรายละเอียดภายในใบงาน เช่น จุดที่ 1 เป็น Order ไหน ส่งให้ลูกค้าคนไหน จำนวนกี่กล่อง และผลการส่งเป็นอะไร

ถ้าเก็บทุกอย่างในตารางเดียว จะทำให้ข้อมูลใบงานซ้ำทุกจุดและแก้ไขยาก การแยกหัวใบงานกับรายการจุดส่งจึงเป็นการออกแบบแบบหนึ่งต่อหลาย และสอดคล้องกับ Class Diagram/Database Design

22. การยืนยันใบงานและการยกเลิก

  1. ก่อนยืนยัน ผลการคำนวณยังเป็นตัวเลือกในหน้าจอ ไม่ควรถือว่าเป็นใบงานจริง
  2. เมื่อกดยืนยัน Backend ต้องตรวจว่าออเดอร์ยังอยู่สถานะที่จัดได้ และ Rider ยังไม่เกินความจุ
  3. บันทึก route plan และ stops ใน Transaction เดียวกัน เพื่อไม่ให้มีหัวใบงานแต่ไม่มีจุดส่ง
  4. เปลี่ยน Order จาก PENDING เป็น ASSIGNED หลังสร้างจุดส่งสำเร็จ
  5. การยกเลิกใบงานควรทำได้เฉพาะก่อนมีผลส่งจริง แล้วคืนออเดอร์กลับเป็น PENDING
  6. ห้ามลบประวัติการส่งที่เป็น DELIVERED เพื่อให้ตรวจสอบย้อนหลังได้

23. การเปลี่ยนสถานะการส่ง

สถานะความหมายการเปลี่ยนที่เหมาะสม
PENDINGยังไม่ได้จัดเข้ารอบรอการคำนวณ/จัดงาน
ASSIGNEDมอบหมายให้อยู่ในใบงานแล้วพร้อมให้ Rider รับไปส่ง
DELIVERINGกำลังนำส่งใช้เมื่อระบบรองรับการเริ่มเที่ยว
DELIVEREDส่งสำเร็จไม่ควรย้อนกลับโดยไม่มีสิทธิ์หรือเหตุผล
FAILEDส่งไม่สำเร็จควรเก็บเหตุผลและกำหนดว่าจะส่งซ้ำหรือคืนงาน
CANCELLEDยกเลิกออเดอร์ไม่ควรนำไปจัดเส้นทาง

24. DFD และการไหลของข้อมูล

Context Diagram: ร้านค้าและ Rider ติดต่อกับระบบ Rider Delivery System; ระบบภายนอกแผนที่ให้ข้อมูลถนน/พิกัด

DFD Level 1: แยกเป็นกระบวนการจัดการลูกค้า, จัดการออเดอร์, วางแผนเส้นทาง, จัดการ Rider และรายงานผลส่ง

DFD Level 2 ของการวางแผน: รับออเดอร์ → ตรวจพิกัด/สถานะ → ขอระยะทางถนน → จัดกลุ่ม Rider → คำนวณเวลา/ต้นทุน → แสดงตัวเลือก → ยืนยัน → บันทึกใบงาน

หลักสำคัญคือผู้ใช้ไม่ควรติดต่อ Database โดยตรง ทุกข้อมูลต้องผ่าน Backend เพื่อให้มี Validation, Authorization และ Transaction

25. คำถามเชิงวิเคราะห์ที่ควรเตรียมตอบ

ถาม: ทำไมไม่ใช้ระยะเส้นตรงอย่างเดียว?
ตอบ: ระยะเส้นตรงเร็วและเหมาะกับการคัดกรอง แต่รถวิ่งตามถนนจริง จึงใช้ OSRM สำหรับระยะทางและเส้นทางสุดท้าย

ถาม: ถ้ามี 25 ออเดอร์และ Rider รับได้ 3 ออเดอร์ ทำไมไม่ใช้แค่ 8 คน?
ตอบ: 8 คนรับได้สูงสุด 24 ออเดอร์ จึงต้องใช้ Rider อย่างน้อย 9 คน หากไม่มีข้อจำกัดอื่น

ถาม: ทำไมบาง Rider ไม่มีงาน?
ตอบ: จำนวนงานอาจน้อยกว่าความจุรวม หรือการแบ่งกลุ่มที่ดีที่สุดไม่จำเป็นต้องใช้ทุกคน ระบบจึงต้องแสดง “ยังไม่มีงานวันนี้” ให้ชัด

ถาม: ถ้า Backend ล่ม หน้าเว็บทำอะไรได้บ้าง?
ตอบ: แสดง loading/error ที่เข้าใจได้ และไม่ควรแสดงข้อมูลปลอมเหมือนบันทึกสำเร็จ

ถาม: ทำไมต้องตรวจซ้ำทั้ง Frontend และ Backend?
ตอบ: Frontend ช่วยให้ผู้ใช้ใช้งานสะดวก แต่ Backend เป็นแนวป้องกันจริง เพราะผู้ใช้สามารถปลอม Request ได้

ถาม: Cache ช่วยอะไร?
ตอบ: ลดการเรียก OSRM ซ้ำเมื่อชุดพิกัดเดิมยังไม่เปลี่ยน ทำให้คำนวณเร็วขึ้น แต่ต้องมีอายุ Cache และล้างเมื่อข้อมูลพิกัด/เส้นทางเปลี่ยน

26. วิธีอ่านโค้ดเวลาต้องอธิบายหน้าหนึ่ง

  1. เริ่มจาก Route ว่า URL นี้ชี้ไป Component ใด
  2. เปิดไฟล์ .ts ดูตัวแปรและฟังก์ชันที่โหลดข้อมูล
  3. ตามชื่อ Service ไปดู URL, Method และ Request Body
  4. ตาม URL ไปดู Backend Controller ว่ารับค่าอะไร
  5. ดู SQL ว่า JOIN ตารางใดและกรองสถานะ/วันที่อย่างไร
  6. ย้อนกลับมาดู HTML ว่าเอาผลลัพธ์ไปแสดงตรงไหน
  7. ถ้ามีการคำนวณ ให้แยก Input → สูตร → Output → จุดที่แสดงผล

รูปแบบการตอบที่ดีคือ “ผู้ใช้กดอะไร → Frontend เรียกอะไร → Backend ตรวจอะไร → Database เปลี่ยนอะไร → หน้าจอแสดงอะไร”

“ระบบนี้แยกหน้าร้านกับหน้าของ Rider ร้านเป็นผู้จัดการลูกค้าและออเดอร์ จากนั้นระบบใช้พิกัดและระยะทางถนนจริงช่วยแบ่งออเดอร์ให้ Rider โดยจำกัดไม่เกิน 3 ออเดอร์ต่อคน ระบบคำนวณระยะทาง เวลา ต้นทุน รายรับ และกำไรก่อนให้ร้านยืนยัน เมื่อยืนยันแล้วจึงสร้าง route plan และ route stop เป็นใบงาน Rider สามารถกรอกเลขใบงานเพื่อดูเฉพาะจุดส่งของตนเอง เปิดแผนที่นำทาง และรายงานผลการส่งได้ ส่วน Backend เป็นผู้ตรวจสิทธิ์ สถานะ และความถูกต้องทั้งหมด”
