Rider Study Guideภาพรวมอ่านโค้ดการคำนวณDatabase/UML/DFDคำถามอาจารย์เจาะลึกโค้ด
หน้าเจาะลึกพิเศษ

โค้ดทำงานจริงอย่างไร ตั้งแต่กดปุ่มจนข้อมูลขึ้นจอ

หน้านี้ตอบคำถามแบบลงรายละเอียดว่าแต่ละฟังก์ชันทำอะไร รับค่าอะไร ส่งค่าอะไร และทำไมข้อมูลจึงไหลไปถึงหน้าถัดไปได้

1. เส้นทางข้อมูลทั้งระบบ

Browser / Angular
  └─ Component เช่น delivery-routes.ts
      └─ API Service เช่น route-api.ts
          └─ HTTP Request เช่น POST /route-plans/road-matrix
              └─ Express Router ใน backend/app.ts
                  └─ Controller ใน backend/controller/route-plan.ts
                      └─ Service หรือ SQL
                          └─ PostgreSQL บน Neon
                              └─ JSON Response กลับไปยัง Angular
                                  └─ signal/state เปลี่ยน
                                      └─ HTML แสดงผลใหม่

การไหลแบบนี้เรียกว่า Separation of Concerns แต่ละชั้นมีหน้าที่ชัดเจน จึงแก้หรือทดสอบได้ง่ายกว่าการเขียนทุกอย่างไว้ใน Component เดียว

2. ตอนเปิดหน้า Delivery Routes เกิดอะไรขึ้น

จุดเริ่มอยู่ที่ frontend/src/app/pages/delivery-routes/delivery-routes.ts โดย Component จะโหลดข้อมูลที่จำเป็น เช่นร้าน ออเดอร์ Rider และแผนเดิม แล้วเก็บไว้ใน state

await Promise.all([
  loadPlanningStore(),
  loadOrders(),
  loadRiders(),
  loadSavedPlans()
]);

แนวคิดของ Promise.all คือข้อมูลที่ไม่ต้องรอกันสามารถโหลดพร้อมกันได้ ลดเวลารอ เมื่อทุก Request สำเร็จจึงนำข้อมูลมาสร้าง Input ให้ตัวคำนวณ

ถ้าขึ้น “โหลดข้อมูลไม่ได้” ให้แยกว่า Error เกิดที่ Request ไหน ไม่ใช่สรุปทันทีว่า Map หรือ Algorithm เสีย

3. ตอนกด “จัดเส้นทาง”

  1. เลือกเฉพาะ Order ของวันปัจจุบันและสถานะที่จัดได้
  2. สร้างรายการพิกัด โดยจุดแรกเป็นร้าน และจุดต่อไปเป็นลูกค้า
  3. เรียก POST /route-plans/road-matrix พร้อม JSON { points: [...] }
  4. Backend ใน route-plan.ts เรียก getRoadDistanceMatrix()
  5. Service ใน road-matrix.ts ส่งพิกัดไป OSRM Table API
  6. ได้ Matrix ที่ตำแหน่งแถว/คอลัมน์แทนจุด และค่าภายในคือระยะทางถนน
  7. Frontend ส่ง Matrix ไป optimizeDeliveryRoutes()
  8. ตัว Optimizer สร้างตัวเลือกหลายแบบ แล้วคำนวณ Score
  9. ผลถูกเก็บใน state เพื่อแสดงการ์ด Rider แผนที่ และตัวเลขสรุป

4. Road Matrix คืออะไร

points = [
  { latitude: ร้าน, longitude: ร้าน },
  { latitude: ลูกค้า A, longitude: ลูกค้า A },
  { latitude: ลูกค้า B, longitude: ลูกค้า B }
]

distancesKm[0][1] = ร้าน → ลูกค้า A
distancesKm[1][2] = ลูกค้า A → ลูกค้า B
distancesKm[2][0] = ลูกค้า B → ร้าน

Matrix เป็นการเตรียมค่าระยะทางระหว่างทุกคู่ไว้ก่อน ทำให้ Algorithm อ่านค่าได้เร็วโดยไม่ต้องเรียก OSRM ทุกครั้งที่ลองสลับจุด

ในโค้ดมีการเก็บ Cache โดยใช้ชุดพิกัดเป็น Key และมีอายุประมาณหนึ่งชั่วโมง เพื่อไม่ให้การคำนวณซ้ำสร้างภาระให้บริการ OSRM

5. จุดที่จัดกลุ่ม Rider อยู่ตรงไหน

การจัดกลุ่มเริ่มจาก frontend/src/app/pages/delivery-routes/planning/route-optimizer.ts และใช้โค้ดพื้นฐานจาก route-assignment.ts

const available = riders.filter(
  rider => rider.status === 'AVAILABLE'
);
const caps = available.map(
  rider => Math.min(3, rider.max_orders_per_route)
);

บรรทัดแรกตัด Rider ที่ไม่พร้อมออก บรรทัดที่สองจำกัดความจุไม่ให้เกิน 3 แม้ฐานข้อมูลจะเก็บค่ามากกว่านั้น

หลังจากนั้น Optimizer ตรวจว่ากลุ่มใดไม่เกินความจุ แล้วประเมินระยะทางขาไป เวลา และต้นทุน ก่อนเลือก Allocation ที่เหมาะกว่า

6. วิธีเลือกผลที่ดีที่สุด

compare(a, b):
  1. เลือกแผนที่จัด Order ได้มากกว่า
  2. ถ้าจัดได้เท่ากัน เลือกแผนที่มีงานล่าช้าน้อยกว่า
  3. ถ้าเท่ากัน เลือกต้นทุนขาออกต่ำกว่า
  4. ถ้าเท่ากัน เลือกเวลารวมต่ำกว่า
  5. ถ้าเท่ากัน เลือกระยะทางต่ำกว่า

เหตุผลที่ต้องมีลำดับความสำคัญคือ “ระยะทางสั้นที่สุด” อย่างเดียวอาจทำให้บางออเดอร์ไม่ได้รับการจัด หรือไปถึงช้า ระบบจึงต้องให้ความสำคัญกับการจัดงานครบและส่งทันก่อน

7. ระยะทางขาไปกับระยะทางกลับร้าน

ในหน้าเลือกเส้นทาง ระบบอาจใช้ระยะทางขาออกเพื่อเปรียบเทียบว่าร้านไปส่งครบเร็วแค่ไหน แต่ตอนคำนวณต้นทุนใบงานต้องรวมเส้นทางกลับร้านด้วย

ร้าน → จุด 1 → จุด 2 → จุด 3 → ร้าน

totalDistance = outboundDistance + returnDistance

นี่คือเหตุผลที่ตัวเลขบนหน้าต่างเลือกแผนอาจต่างจากตัวเลขในใบงานที่บันทึกแล้วได้ หากส่วนหนึ่งใช้เพื่อจัดลำดับและอีกส่วนใช้บัญชีต้นทุน ต้องอ่านชื่อฟังก์ชันและตัวเลือก includeReturnDistance ประกอบ

8. สูตรคำนวณในไฟล์ planning

ไฟล์ฟังก์ชัน/หน้าที่ผลลัพธ์
route-distance.tsคำนวณระยะทาง Haversine และรวมช่วงร้าน/จุดส่ง/กลับร้านstops, distanceFromPrevious, totalDistanceKm
route-timing.tsคำนวณเวลาถึงจากระยะทาง ความเร็ว เวลาออก และ Deadlinearrival, lateOrderCount, totalMinutes
route-cost.tsคำนวณรายรับ ต้นทุน ค่ารอบ ค่าเดินทาง และกำไรtotalRevenue, totalCost, totalProfit
route-assignment.tsสร้างกลุ่มเริ่มต้นตาม Rider และความจุtrips/assignments
route-optimizer.tsลองหลาย Allocation และจัดลำดับจุดที่เหมาะสมRoutePlanAlternative[]

9. ตอนกดบันทึก/ยืนยันใบงาน

ปุ่มยืนยันไม่ได้ส่งแค่ชื่อ Rider แต่ส่งแผนที่เลือกทั้งชุดกลับ Backend ผ่าน POST /route-plans/confirm ซึ่งเป็น Alias เดียวกับ /generate

Payload แนวคิดคือ:

{
  storeId,
  routeDate,
  trips: [
    {
      riderId,
      totalBoxes,
      stops: [
        { orderId, sequence, distanceFromPreviousKm }
      ],
      totalDistanceKm,
      estimatedMinutes,
      totalCost,
      totalRevenue,
      totalProfit,
      worksheetCode
    }
  ]
}

Backend ใน selected-plan.ts ตรวจข้อมูลอีกครั้ง แล้วใช้ Database Transaction สร้าง route_plans, สร้าง route_stops, เปลี่ยน orders.status เป็น ASSIGNED และ Commit พร้อมกัน

ถ้าขั้นตอนใดล้มเหลว ระบบควร Rollback เพื่อไม่ให้เกิดกรณีมีใบงานแต่ไม่มีจุดส่ง หรือ Order ถูก ASSIGNED แต่ไม่มีใบงาน

10. Worksheet Code และ QR ทำงานอย่างไร

Worksheet Code ถูกสร้างหรือเก็บอยู่กับใบงานใน route_plans.worksheet_code จากนั้นหน้า Riders สร้าง URL Login เช่น:

https://frontend.example/rider/login
  ?worksheetCode=WORK-R01-DEMO

ในไฟล์ frontend/src/app/pages/riders/riders.ts ฟังก์ชัน qrLoginUrl() สร้าง URL และ qrImageUrl() ส่ง URL ไปยัง QR Image API เพื่อสร้างรูป QR

return 'https://api.qrserver.com/v1/create-qr-code/'
  + '?size=240x240&data='
  + encodeURIComponent(loginUrl);

QR ไม่ได้เปิดงานด้วยเวทมนตร์ แต่เก็บ URL ไว้ เมื่อกล้องอ่าน QR จะเปิด URL เดิม ทำให้ Browser เข้าหน้า Login พร้อม Query Parameter

เหตุผลที่เปิดใบงานต่อได้เองอยู่ที่ rider-login.ts อ่าน worksheetCode จาก Query Param แล้วเรียก executeLogin() อัตโนมัติ

11. Login ส่งค่าอะไร

rider-login.ts
  queryCode = ActivatedRoute.queryParamMap.get('worksheetCode')
  executeLogin(queryCode)

rider-auth-api.ts
  POST /rider/auth/worksheet
  body: { worksheetCode }

response:
  { worksheetCode, rider }

Service เก็บ Code ไว้ใน localStorage ด้วย Key rider_worksheet_code จากนั้นหน้า Work ใช้ Code นี้ทำ Header:

x-worksheet-code: WORK-R01-DEMO

จุดสำคัญคือ Backend ไม่รับ rider_id จากหน้าจอเพื่อเชื่อใจทันที แต่ใช้ Code ไปค้นหาใบงานที่ valid ของวันนั้น แล้วได้ riderId และ routePlanId จากฐานข้อมูล

12. Backend รู้ได้อย่างไรว่าใบงานเป็นของ Rider คนไหน

Middleware backend/middleware/rider-session.ts รับ Header แล้วค้นหาโดย JOIN ตาราง:

route_plans.worksheet_code
  → route_plans.route_plan_id
  → route_stops.route_plan_id
  → route_stops.rider_id
  → riders.rider_id

นอกจาก Code ต้องตรง ยังตรวจวันทำงานและสถานะใบงานเป็น SELECTED ด้วย ถ้าไม่ผ่านจะตอบ 401/403 และหน้า Work ไม่ควรแสดงข้อมูล

13. หน้า Rider Work ดึงข้อมูลอะไร

ไฟล์ backend/controller/rider.ts Endpoint GET /rider/work ใช้ข้อมูลจาก route stop, route plan, store, order และ customer แล้วรวมเป็น JSON งานหนึ่งชุด:

work: {
  workDate,
  totalBoxes,
  totalStops,
  deliveredStops,
  pendingStops,
  storeName,
  storePhone,
  storeLatitude,
  storeLongitude,
  stops: [
    {
      routeStopId,
      sequence,
      orderId,
      customerName,
      address,
      boxes,
      latitude,
      longitude,
      status
    }
  ]
}

หน้า rider-work.ts เรียก getMe() และ getWork() พร้อมกันด้วย Promise.all แล้วแสดงชื่อ Rider จากข้อมูล me และแสดงจุดส่งจาก work

14. หน้า Rider เช็คว่ามีออเดอร์หรือยังอย่างไร

หน้า Riders เรียก GET /rider Backend ใช้ LEFT JOIN กับจุดส่งของวันนี้ ทำให้ Rider ที่ไม่มีงานยังปรากฏได้ แต่จำนวนงานเป็น 0

COUNT(today_stops.rider_id) AS order_count
SUM(today_stops.box_quantity) AS total_box_count
FILTER (WHERE delivery_status = 'DELIVERED')
FILTER (WHERE delivery_status = 'PENDING')

จึงแสดงแยกได้ว่า Rider คนนี้มีงานวันนี้หรือยัง ส่งไปกี่ออเดอร์ เหลือกี่ออเดอร์ และมีกี่กล่อง

15. แผนที่ในเว็บสร้างอย่างไร

แผนที่ใช้ Leaflet เป็นตัวควบคุมแผนที่และใช้ MapTiler เป็นแหล่ง Tile ภาพแผนที่ ขั้นตอนทั่วไปคือ:

  1. สร้าง L.map(element) ผูกกับ div
  2. สร้าง Tile Layer โดยใช้ URL ของ MapTiler และ API Key จาก Environment
  3. เพิ่ม Marker จาก latitude/longitude ของร้านและลูกค้า
  4. เรียก OSRM Route API เพื่อขอพิกัดแนวถนน
  5. สร้าง L.polyline(geometry) แล้วเพิ่มลงแผนที่
  6. เรียก fitBounds ให้แผนที่ครอบคลุมจุดทั้งหมด

MapTiler ทำให้เห็นพื้นหลังแผนที่ ส่วน OSRM ทำให้เส้นทางเป็นถนนจริง ทั้งสองอย่างเป็นคนละหน้าที่กัน

16. ทำไมเส้นทางถึงตรงตามถนนจริง

ถ้าเอาพิกัดร้านกับลูกค้ามาต่อกันตรง ๆ จะเป็นเส้นตรงและไม่ใช่เส้นทางรถ แต่ระบบส่งพิกัดไป OSRM ซึ่งอ้างอิงข้อมูลถนนจาก OpenStreetMap และคืนชุดพิกัดตามแนวถนน เช่น:

OSRM response
  routes[0].geometry.coordinates
        ↓
  convert [longitude, latitude]
        ↓
  Leaflet expects [latitude, longitude]
        ↓
  L.polyline(roadPoints)

ความแม่นยำขึ้นกับคุณภาพข้อมูลถนน พิกัดลูกค้า และบริการ Routing ไม่ใช่แค่ความสวยของแผนที่ ถ้าพิกัดผิด เส้นทางก็ผิดตาม

17. ปุ่มเปิด Google Maps ทำอะไร

หน้า Rider สร้าง URL ไป Google Maps Directions API ด้วยพิกัดปลายทาง เช่น https://www.google.com/maps/dir/?api=1&destination=lat,long การกดปุ่มไม่ได้คำนวณเส้นทางใน Backend แต่ส่งต่อให้ Google Maps นำทางจากตำแหน่งปัจจุบันของมือถือ

18. PostgreSQL คืออะไร

PostgreSQL คือระบบจัดการฐานข้อมูลเชิงสัมพันธ์แบบ Open Source ใช้ SQL และมีความสามารถด้าน Constraint, Foreign Key, Transaction, Index, JOIN และชนิดข้อมูลที่เหมาะกับงานจริง

ระบบนี้เหมาะกับ PostgreSQL เพราะข้อมูลมีความสัมพันธ์ชัดเจน เช่น Order ต้องอ้าง Customer, Route Stop ต้องอ้าง Order/Rider/Route Plan และการยืนยันใบงานต้องเปลี่ยนหลายตารางพร้อมกันอย่างปลอดภัย

Transaction สำคัญ: ถ้าบันทึกใบงานสำเร็จแต่เปลี่ยน Order ไม่สำเร็จ ข้อมูลจะขัดแย้งกัน PostgreSQL สามารถ Commit ทั้งชุดหรือ Rollback ทั้งชุดได้

19. Neon คืออะไร และต่างจาก Supabase อย่างไร

หัวข้อNeonSupabase
พื้นฐานบริการ PostgreSQL แบบ Cloud/Serverlessแพลตฟอร์ม Backend-as-a-Service ที่มี PostgreSQL เป็นแกน
จุดเด่นแยก Compute/Storage, Branching Database, เหมาะกับ Connection String PostgreSQLมี Auth, Storage, Realtime, API และ Dashboard มาให้
สิ่งที่โปรเจกต์ใช้ใช้เป็น PostgreSQL แล้ว Backend ต่อด้วย pgไม่ได้ใช้ Supabase SDK เป็นหลัก
เหตุผลที่เลือกทีมมี Schema และ SQL อยู่แล้ว ต้องการฐานข้อมูล PostgreSQL ตรง ๆเหมาะเมื่ออยากใช้ระบบ Login/Storage/Realtime ที่มีให้ในตัว

Neon ไม่ใช่ฐานข้อมูลคนละประเภทกับ PostgreSQL แต่เป็นผู้ให้บริการ PostgreSQL บน Cloud ส่วน Supabase ก็ใช้ PostgreSQL เช่นกัน แต่เพิ่มบริการรอบข้างมาให้มากกว่า

20. Deploy Frontend และ Backend

Frontend

  1. เชื่อม Git Repository หรือเลือกโฟลเดอร์ที่มี Angular
  2. ตั้ง Root Directory เป็น frontend ถ้า Repository มี frontend/backend อยู่ด้วยกัน
  3. Build Command ใช้คำสั่งจาก frontend/package.json เช่น npm run build
  4. Output Directory ต้องตรงกับ Angular ที่ Build จริง เช่น dist/frontend ไม่ใช่ public โดยต้องตรวจชื่อจริงใน Build Log
  5. เพิ่ม MAPTILER_API_KEY ใน Environment ของ Frontend โดยไม่ใส่ลง Source Code
  6. ตั้ง API Endpoint ให้ชี้ไป Backend URL

Backend

  1. ตั้ง Root Directory เป็น backend
  2. ตั้ง Build/Install ตาม backend/package.json
  3. เพิ่ม DATABASE_URL ใน Vercel Environment ของ Backend
  4. เพิ่ม Secret ที่ Backend ต้องใช้ถ้ามี
  5. เพิ่ม Frontend Production Domain ใน CORS ของ Backend
  6. Deploy แล้วทดสอบ Endpoint จริง เช่น /route-plans

27. ตัวอย่าง SQL ที่ทำให้รู้ว่าใบงานเป็นของใคร

FROM route_plans AS route_plan
INNER JOIN route_stops AS route_stop
  ON route_stop.route_plan_id =
     route_plan.route_plan_id
INNER JOIN riders AS rider
  ON rider.rider_id = route_stop.rider_id
WHERE route_plan.worksheet_code = $1
  AND route_plan.route_date = BUSINESS_DATE
  AND route_plan.status = 'SELECTED'

$1 คือ Worksheet Code ที่ส่งจาก Header ไม่ใช่ค่าที่ต่อ String ลง SQL โดยตรง การใช้ Parameterized Query ช่วยป้องกัน SQL Injection และช่วยให้ฐานข้อมูลจัดการชนิดข้อมูลได้ถูกต้อง

ถ้า Code ตรงแต่ใบงานเป็นของวันเก่า หรือสถานะไม่ใช่ SELECTED ก็จะไม่ผ่านการตรวจ

36. ทำไมไม่ใช้ Supabase

Supabase ก็ใช้ PostgreSQL แต่มีบริการ Auth, Storage, Realtime และ Auto API รอบฐานข้อมูล หากทีมเลือก Supabase จะต้องออกแบบการเชื่อมต่อและสิทธิ์ให้เข้ากับ Supabase Client/RLS

โปรเจกต์นี้ใช้ Express ควบคุมกฎธุรกิจและใช้แพ็กเกจ PostgreSQL pg ต่อ Neon โดยตรง ดังนั้นเปลี่ยนไป Supabase ไม่ใช่แค่เปลี่ยน URL แต่ต้องพิจารณา Auth, API, Security Policy และวิธี Query ใหม่
