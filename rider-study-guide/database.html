1. ตารางหลัก

ตารางเก็บอะไรคำถามที่ตอบได้
storesชื่อร้าน พิกัด จุดเริ่มงานอาหารเริ่มจากที่ไหน?
customersชื่อ เบอร์ ที่อยู่ latitude longitudeต้องส่งให้ใครและอยู่ตรงไหน?
ridersชื่อ เบอร์ ทะเบียน สถานะ ความจุใครพร้อมรับงานและรับได้กี่ออเดอร์?
ordersลูกค้า จำนวนกล่อง วันที่ สถานะวันนี้มีงานกี่รายการ?
route_plansใบงาน วันที่ Rider ระยะทาง เวลา เงิน และ Worksheet Codeแต่ละรอบให้ใครและมีภาพรวมเท่าไร?
route_stopsจุดส่ง ลำดับ Order สถานะผลส่งต้องไปจุดไหนก่อนและส่งสำเร็จหรือยัง?

2. ความสัมพันธ์

Store 1 ───< RoutePlan 1 ───< RouteStop >─── 1 Order >─── 1 Customer
                    │                 │
                    └──── Rider ──────┘

เครื่องหมาย 1:N หมายถึงด้านหนึ่งมีหลายรายการ เช่น ร้านหนึ่งมีหลายใบงาน และใบงานหนึ่งมีหลายจุดส่ง

การใช้ Foreign Key ทำให้ไม่สามารถสร้างจุดส่งที่อ้างถึง Order หรือ Rider ที่ไม่มีอยู่จริงได้ และช่วยป้องกันข้อมูลกำพร้า

3. Class Diagram ที่แปลงเป็นระบบจริง

Class ในแบบจำลองข้อมูล/พฤติกรรมในระบบ
Customerข้อมูลส่วนตัวสำหรับจัดส่งและพิกัด
Orderจำนวนกล่อง วันที่ และการเปลี่ยนสถานะ
Riderข้อมูลคนส่ง สถานะ และความจุ
RoutePlanผลการจัดกลุ่มและตัวเลขสรุป
RouteStopความสัมพันธ์ระหว่างใบงานกับ Order และลำดับจุด
RoutingServiceขอระยะทาง/Geometry จาก OSRM

5. Include, Extend และ Generalization

Include: Use Case หลักต้องเรียกขั้นตอนย่อย เช่น “ยืนยันใบงาน” include “ตรวจว่า Order ยัง PENDING” และ “ตรวจความจุ Rider”

Extend: พฤติกรรมเสริมที่เกิดเฉพาะบางกรณี เช่น “เปิด Google Maps” extend จาก “ดูจุดส่ง” หรือ “ส่งไม่สำเร็จ” extend จาก “รายงานผลส่ง”

Generalization: ถ้ามีผู้ใช้หลายประเภทที่มีพฤติกรรมร่วมกัน อาจมี User เป็นแม่ และ Store/Rider เป็นผู้ใช้เฉพาะ แต่ระบบปัจจุบันแยกหน้าตามบทบาทเป็นหลัก

6. DFD ระดับต่าง ๆ

ระดับสิ่งที่แสดงตัวอย่าง
Context Diagramระบบเป็นกล่องเดียวและ Actor ภายนอกร้านค้า/Rider ↔ ระบบจัดส่ง
Level 1กระบวนการหลักหลายส่วนCustomer, Order, Planning, Rider Work
Level 2แตกกระบวนการหนึ่งให้ละเอียดตรวจ Order → ขอ OSRM → จัดกลุ่ม → คำนวณ → ยืนยัน

Balancing: ข้อมูลเข้า/ออกของ Level 1 ต้องสอดคล้องกับ Context Diagram ไม่ควรมีข้อมูลใหม่ที่ไม่อธิบายที่ระดับบน

7. Data Dictionary

Fieldชนิดโดยแนวคิดเหตุผล
rider_id/order_id/route_plan_idInteger Primary Keyระบุรายการไม่ซ้ำ
box_quantitySmall Integerจำนวนกล่องไม่ควรเป็นทศนิยม

8. ความปลอดภัยและ Validation

Validation ฝั่ง Frontend ช่วยแจ้งเตือนเร็ว แต่ Backend ต้องตรวจซ้ำ เช่น จำนวนกล่องต้องอยู่ในช่วงที่กำหนด, พิกัดต้องอยู่ในรัศมีร้าน, Order ต้องเป็นวันที่ถูกต้อง และ Route Stop ต้องเป็นของ Worksheet ที่ส่งมา

หลักการนี้ตอบคำถามเรื่อง Security ได้ว่า “ผู้ใช้ไม่ควรเข้าถึงข้อมูลโดยแก้ค่าใน Browser เพราะ Backend ตรวจความสัมพันธ์ของข้อมูลและสิทธิ์อีกครั้ง”
