หน้า 4: ซ้อมตอบ

คำถามที่อาจารย์อาจถามและวิธีตอบ

ตอบโดยใช้โครงสร้าง “เหตุผลทางธุรกิจ → วิธีออกแบบ → หลักฐานในโค้ด → ผลลัพธ์” อย่าตอบแค่ว่า “ระบบทำได้” แต่บอกว่าทำอย่างไร

คำถามเรื่องปัญหาและความต้องการ

ถาม: ระบบนี้แก้ปัญหาอะไร?

แก้การแบ่งงานและการเลือกเส้นทางที่ไม่เป็นระบบในช่วงออเดอร์หนาแน่น โดยพิจารณาพิกัด ระยะทางถนน ความจุ Rider เวลา และต้นทุน เพื่อให้ร้านตรวจและยืนยันใบงานได้

ถาม: ทำไมต้องมีสองฝั่ง?

ร้านต้องจัดข้อมูลและตัดสินใจ ส่วน Rider ต้องใช้ข้อมูลที่สรุปง่ายบนมือถือและรายงานผลส่ง จึงแยกสิทธิ์และหน้าที่ให้เหมาะกับผู้ใช้

ถาม: ระบบรับประกันว่าส่งทัน 100% หรือไม่?

ไม่รับประกันแบบแน่นอน เพราะรถติดและสถานการณ์จริงเปลี่ยนได้ ระบบให้เวลาประมาณการเพื่อช่วยเลือกแผนที่มีความเสี่ยงต่ำกว่า

คำถามเรื่อง OOP และ Angular

ถาม: Component คืออะไร?

เป็นหน่วยของ Angular ที่รวม Template, Logic และการแสดงผลของหน้าหนึ่งไว้ด้วยกัน เช่นหน้า Orders หรือ Delivery Routes

ถาม: Service มีไว้ทำไม?

แยกการเรียก API ออกจาก Component ทำให้โค้ดหน้าเว็บอ่านง่าย ใช้ซ้ำได้ และเปลี่ยน URL/API ได้จากจุดเดียว

ถาม: ทำไมไม่ให้ Component ต่อ Database?

เพราะ Frontend ไม่ควรถือสิทธิ์ฐานข้อมูลโดยตรง ต้องผ่าน Backend เพื่อควบคุม Validation, Security และ Business Rule

ถาม: Encapsulation อยู่ตรงไหน?

รายละเอียดการเรียกฐานข้อมูลและการคำนวณถูกซ่อนใน Service/Controller ผู้เรียกใช้ไม่ต้องรู้ SQL ภายในทั้งหมด

คำถามเรื่อง Use Case

ถาม: Actor มีใครบ้าง?

เจ้าของร้าน, Rider และระบบภายนอกอย่าง OSRM/MapTiler/Google Maps โดย Actor คือผู้ที่มีปฏิสัมพันธ์กับระบบ ไม่ใช่ตาราง Database

ถาม: Use Case “ยืนยันใบงาน” มี Include อะไร?

ตรวจ Order ที่เลือก, ตรวจ Rider ที่พร้อม, ตรวจความจุ, คำนวณ/ตรวจตัวเลข และบันทึกข้อมูลเป็น Transaction

ถาม: Use Case ใดเป็น Extend?

เปิด Google Maps หรือรายงานส่งไม่สำเร็จเป็นพฤติกรรมเสริมที่เกิดจากบางเงื่อนไขของการดูหรือส่งจุดงาน

คำถามเรื่อง Class Diagram และ Database

ถาม: ทำไมต้องแยก RoutePlan กับ RouteStop?

RoutePlan เป็นข้อมูลสรุปของเที่ยว ส่วน RouteStop เป็นรายการจุดส่งหลายจุด การแยกทำให้ไม่ต้องเก็บข้อมูลสรุปซ้ำในทุกจุด และรองรับการเรียงลำดับ/เปลี่ยนสถานะรายจุด

ถาม: Customer กับ Order เป็นความสัมพันธ์แบบใด?

Customer หนึ่งคนสามารถมีหลาย Order ได้ ส่วน Order หนึ่งรายการอ้างถึง Customer หนึ่งคน จึงเป็น 1:N

ถาม: Foreign Key ช่วยอะไร?

ป้องกันการอ้างอิงข้อมูลที่ไม่มีอยู่จริง เช่นสร้าง Route Stop ให้ Rider ที่ไม่มีในระบบ และช่วยรักษาความถูกต้องของความสัมพันธ์

ถาม: ทำไมต้องมี status?

เพื่อแยกวงจรชีวิตของข้อมูล เช่นออเดอร์ที่ยังรอจัด งานที่มอบหมายแล้ว และงานที่ส่งสำเร็จ ซึ่งแต่ละสถานะอนุญาตการทำงานไม่เหมือนกัน

คำถามเรื่อง DFD

ถาม: DFD ต่างจาก Flowchart อย่างไร?

DFD เน้นการไหลของข้อมูลระหว่าง Actor, Process และ Data Store ส่วน Flowchart เน้นลำดับขั้นตอนและเงื่อนไขของการทำงาน

ถาม: Data Store ของระบบคืออะไร?

ฐานข้อมูล PostgreSQL ซึ่งเก็บ Stores, Customers, Riders, Orders, Route Plans และ Route Stops

ถาม: อะไรคือ Process หลัก?

จัดการลูกค้า, จัดการออเดอร์, คำนวณเส้นทาง, ยืนยันใบงาน, เปิดใบงาน Rider และอัปเดตผลการส่ง

คำถามเรื่อง Algorithm

ถาม: ทำไมไม่เรียงตาม Order ID?

Order ID เป็นเพียงเลขประจำข้อมูล ไม่ได้บอกตำแหน่งลูกค้า การใช้พิกัดและระยะทางถนนช่วยให้จุดที่อยู่ใกล้กันถูกพิจารณาอยู่ในรอบเดียวกัน

ถาม: Algorithm นี้เป็น Optimal 100% ไหม?

ไม่จำเป็นต้องอ้างว่า Optimal 100% ระบบใช้ Heuristic และการปรับปรุงหลายทางเลือกเพื่อหาผลที่ดีภายในเวลาที่เหมาะสม เพราะปัญหาการจัดเส้นทางมีความซับซ้อนสูง

ถาม: ถ้ามี 25 ออเดอร์ Rider รับได้ 3 ออเดอร์ ต้องใช้กี่คนขั้นต่ำ?

ต้องใช้เพดาน 25 ÷ 3 แล้วปัดขึ้นเป็น 9 คน เพราะ 8 คนรับได้สูงสุด 24 ออเดอร์

ถาม: ทำไมบาง Rider ไม่มีงาน?

ถ้าจำนวนงานไม่พอหรือการจัดกลุ่มไม่จำเป็นต้องใช้ทุกคน Rider บางคนอาจมีงานเป็นศูนย์ ระบบควรแสดงสถานะ “ยังไม่มีงานวันนี้” ให้ชัด

คำถามเรื่องการทดสอบและ Error

ถาม: ถ้า API ได้ 500 ตรวจตรงไหน?

ตรวจ Response และ Backend terminal ก่อน เพราะ 500 มักเกิดจาก SQL, Column ไม่ตรง, JOIN กำกวม หรือ Environment/Database ไม่พร้อม

ถาม: ถ้าเป็น CORS ตรวจอะไร?

ตรวจ Origin ของ Frontend, allowed origins ใน backend/app.ts, allowed header x-worksheet-code และ OPTIONS preflight

ถาม: ถ้าแผนที่เป็น Invalid key?

ตรวจค่า MapTiler API Key ของ Environment ที่ Deploy ใช้และ Allowed HTTP Origins ของ Key โดยไม่เปิดเผยค่า Key ในรายงาน

ถาม: ทดสอบการยกเลิกใบงานอย่างไร?

สร้างงาน → ยืนยัน → ตรวจ Order เป็น ASSIGNED → ยกเลิกก่อนมีผลส่ง → ตรวจ Route Plan ไม่ถูกเลือกและ Order กลับ PENDING → โหลดหน้าใหม่เพื่อยืนยันว่าไม่ค้าง

สคริปต์พูดนำเสนอ 1 นาที

“โปรเจกต์นี้ช่วยร้านข้าวกล่องจัดส่งในช่วงเวลาจำกัด ร้านจัดการลูกค้าและออเดอร์ จากนั้นระบบกรองออเดอร์ของวัน ตรวจพิกัด และเรียก OSRM เพื่อหาระยะทางตามถนน ระบบแบ่งงานให้ Rider โดยไม่เกิน 3 ออเดอร์ต่อรอบ และเปรียบเทียบระยะทาง เวลา ต้นทุน และกำไร ก่อนสร้าง Route Plan กับ Route Stop เมื่อร้านยืนยัน Rider จะใช้ Worksheet Code เปิดงานบนมือถือ ดูจุดส่งตามลำดับ เปิดแผนที่ และรายงานผลส่ง Backend เป็นผู้ตรวจสถานะและความถูกต้องเพื่อไม่ให้ข้อมูลแต่ละส่วนขัดแย้งกัน”

สิ่งที่ไม่ควรตอบเกินจริง

  • อย่าบอกว่าเส้นทางดีที่สุด 100% ถ้ายังเป็น Heuristic
  • อย่าบอกว่าเวลาถึงเป็นเวลาจริงที่รับประกัน
  • อย่าบอกว่า Frontend ปลอดภัยเพียงเพราะซ่อนปุ่ม
  • อย่าบอกว่าออเดอร์เก่าหายไป เพราะจริง ๆ ควรกรองตามวันหรือสถานะ
  • อย่าเปิดเผย Secret, Database URL หรือ API Key ตอนนำเสนอ
ใช้หน้านี้ซ้อมตอบ แล้วกลับไปดูหลักฐานโค้ดใน หน้าอ่านโค้ด
